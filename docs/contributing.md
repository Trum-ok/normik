# Как добавить правило

Добавление правила — это один новый файл в `src/nk/rules/` и один каталог
в `tests/fixtures/`. Ничего больше править не нужно: реестр находит правило
по декоратору, тесты — по имени каталога.

## Рецепт

1. Найти пункт ГОСТ 7.32-2017, который проверяете, и выписать его номер.
2. Придумать идентификатор: `G732-<пункт>-<мнемоника>`, например
   `G732-6.5.7-caption-dot`. Мнемоника нужна потому, что на один пункт
   приходится несколько независимых проверок.
3. Создать файл в подпапке по разделу стандарта:
   - `rules/structure/` — разделы 4 и 5: состав и требования к структурным элементам;
   - `rules/layout/` — подразделы 6.2 и 6.4: построение отчёта и нумерация рубрик;
   - `rules/elements/` — подразделы 6.5–6.9, 6.12, 6.16, 6.17: иллюстрации,
     таблицы, формулы, ссылки, реферат, источники, приложения.
4. Создать `tests/fixtures/<id>/bad.tex` и `tests/fixtures/<id>/good.tex`.
5. Написать докстринг правила — из него собирается страница документации.
6. Прогнать `make check` и `uv run nk rules docs`.

## Полный пример

`src/nk/rules/elements/figure_caption_dot.py`:

```python
"""Точка в конце наименования рисунка."""

from collections.abc import Iterable

from nk.core.document import Document
from nk.core.finding import Finding, Severity
from nk.core.rule import rule
from nk.rules._shared import FIGURE_ENVIRONMENTS, caption_text, captions, one_line


@rule(
    id="G732-6.5.7-caption-dot",
    clause="6.5.7",
    severity=Severity.ERROR,
    title="Наименование рисунка заканчивается точкой",
)
def figure_caption_dot(doc: Document) -> Iterable[Finding]:
    r"""Проверяет наименование рисунка на точку в конце. Точка внутри
    наименования нарушением не является.

    ## Почему это нарушение

    Наименование рисунка приводят с прописной буквы без точки в конце.

    ## Как исправить

    Убрать точку в конце `\caption`.
    """
    for environment in doc.structure.find_environments(*FIGURE_ENVIRONMENTS):
        for command in captions(environment):
            text = caption_text(command)
            if not text.endswith("."):
                continue
            yield figure_caption_dot.finding(
                doc,
                command.span,
                message="Наименование рисунка заканчивается точкой.",
                requirement="Наименование рисунка приводят с прописной буквы без точки в конце.",
                suggestion=f"\\{command.name}{{{one_line(text[:-1])}}}",
                col=command.col,
            )
```

Разбор по частям:

- **Декоратор** объявляет метаданные один раз. `id`, `clause`, `severity` и `title`
  больше нигде повторять не нужно.
- **Докстринг** — источник страницы правила в документации, см.
  [ниже](#описание-правила).
- **Сигнатура** фиксирована протоколом `Rule` и проверяется `ty`: правило принимает
  `Document` и возвращает `Iterable[Finding]`.
- **Правило — чистая функция.** Никакого ввода-вывода, никакого состояния между
  вызовами, никакого чтения файлов помимо того, что уже в `Document`.
- **`figure_caption_dot.finding(...)`** — обращение правила к самому себе по имени.
  Оно разрешается в момент вызова, когда декоратор уже отработал. Метод сам
  проставляет `rule_id`, `clause`, `severity` с учётом профиля, `excerpt` и `context`.
- **Позиция.** Первым позиционным аргументом идёт `Line` или `Span`; `col`
  указывается отдельно, если известна колонка.

## Что видит правило

`Document` хранит два представления одного исходника.

**Построчное** — для проверок, где важен текст строки:

```python
for line in doc.iter_lines():
    line.raw       # исходная строка
    line.stripped  # без комментария (с учётом экранированного \% и аргумента \verb)
    line.lineno    # номер строки, с единицы
    line.path      # файл, а не файл-агрегатор
```

**Структурное** — для проверок, где важна вложенность:

```python
doc.structure.find_environments("figure", "table")  # окружения по именам
doc.structure.find_commands("caption", "label")     # команды по именам
doc.structure.enclosing(path, lineno)               # самое внутреннее окружение
environment.children                                # вложенные окружения
environment.commands                                # команды непосредственно внутри
environment.all_commands()                          # включая вложенные окружения
```

Команды внутри аргументов других команд сканер видит наравне с остальными:
`\caption{Схема\label{fig:a}}` даёт и `caption`, и `label`, а `\ref` в сноске
или в `\textbf` — обычную ссылку. Тела определений макросов (`\newcommand`,
`\def`, `\newenvironment`) не сканируются.

Готовые помощники — в `src/nk/rules/_shared.py`: наборы имён окружений, извлечение
текста подписи, метки и ссылки, наименования структурных элементов. Прежде чем
писать свой разбор, посмотрите, нет ли там нужного.

## Описание правила

Докстринг функции правила — источник его страницы в документации. Он пишется
на Markdown и попадает на страницу как есть, поэтому заголовки в нём — второго
уровня.

```python
def figure_caption_dot(doc: Document) -> Iterable[Finding]:
    """Проверяет наименование рисунка на точку в конце. Точка внутри
    наименования нарушением не является.

    ## Почему это нарушение

    Наименование рисунка приводят с прописной буквы без точки в конце: оно
    образует с номером единую подпись, а не предложение.

    ## Как исправить

    Убрать точку в конце `\caption`.
    """
```

- **Первый абзац** — что правило ищет и чего не трогает. Сюда же выносятся
  известные ограничения: случаи, в которых по исходникам решить нельзя.
- **«Почему это нарушение»** — смысл требования своими словами. Не «так
  написано в стандарте», а что ломается, если сделать иначе.
- **«Как исправить»** — что сделать в исходнике.

Если в докстринге есть обратная косая — а она есть, как только появляется
пример LaTeX, — объявляйте его сырым: `r"""`.

Пример нарушения и правильного оформления на страницу подставляются из фикстур
правила, писать их отдельно не нужно. Показывается файл целиком; если он
длинный, покажите его часть, обрамив её метками:

```latex
% DOC-BEGIN
\begin{figure}
  \includegraphics{img/setup.png}
  \caption{Схема экспериментальной установки}
\end{figure}
% DOC-END
```

## Правка для `--fix`

Если исправление однозначно, правило может объявить машинную правку — тогда
`nk check --fix` применит её сам. Частый случай: `suggestion` и есть готовая
замена, тогда достаточно указать заменяемый регион:

```python
yield figure_caption_dot.finding(
    doc,
    command.span,
    message="Наименование рисунка заканчивается точкой.",
    requirement="Наименование рисунка приводят с прописной буквы без точки в конце.",
    suggestion=f"\\{command.name}{{{one_line(text[:-1])}}}",
    col=command.col,
    fix=command.region,          # заменить команду целиком текстом suggestion
)
```

`command.region` — точные границы команды вместе с аргументами, включая
многострочные. Правило с правками объявляется с `fixable=True`; тест сверяет
объявление с действительностью, поэтому соврать не получится.

Когда заменяемый текст отличается от подсказки — например подсказка говорит
«убрать двоеточие», а заменить нужно один символ на пустую строку, — передаётся
готовый `Fix`:

```python
fix=Fix(Region.in_line(line.path, line.lineno, colon, colon + 1), "")
```

Точный кусок исходника под регионом даёт `doc.slice(region)` — им удобно строить
замену «то же самое, но без чего-то»:

```python
fix=Fix(command.region, doc.slice(command.region).replace("\\-", ""))
```

**Правку объявляют, только когда замена однозначна.** «Перенести подпись ниже
рисунка», «добавить ссылку в текст», «заменить «рис.» на «рисунок»» правками не
являются: в первых двух нужно решение о структуре, в третьем — согласование
падежа. Такие правила ограничиваются `suggestion`.

Тест на фикстурах проверяет правки сам: применяет их к `bad.tex` в несколько
проходов и требует, чтобы находки с правками исчезли и новых не появилось.

## Требования к тексту находки

Это самая частая точка деградации, поэтому требование проверяется на ревью.
Находка должна быть самодостаточна: по ней нарушение исправляется руками или
передачей вывода `--format agent` в Claude Code, без дополнительных пояснений.
Читающий не обязан открывать ГОСТ или `docs/RULES.md`.

- **`message`** — что не так, одной фразой, про конкретное место.
  Плохо: `Нарушение п. 6.5.7`. Хорошо: `Наименование рисунка заканчивается точкой.`
- **`requirement`** — что требуется, **своими словами**. Цитировать стандарт нельзя:
  ГОСТ 7.32-2017 не является общественным достоянием, и его текста в репозитории нет.
  Плохо: `См. п. 6.5.7`. Хорошо: `Наименование рисунка приводят с прописной буквы
  без точки в конце.`
- **`suggestion`** — конкретное действие или готовый фрагмент на замену.
  Плохо: `Исправьте оформление`. Хорошо: `\caption{Схема экспериментальной установки}`.

`suggestion` обязателен. Если исправление принципиально неоднозначно, объявите
правило с `allow_missing_suggestion=True` — тест это проверяет.

## Фикстуры

`bad.tex` — файл с нарушениями. Каждая строка, где правило обязано сработать,
помечается комментарием `% EXPECT`:

```latex
\begin{figure}
  \includegraphics{img/setup.png}
  \caption{Схема экспериментальной установки.} % EXPECT
\end{figure}
```

Сопоставление строгое в обе стороны: множество строк с находками должно совпадать
с множеством помеченных строк. Лишняя находка и пропущенная пометка одинаково
роняют тест.

Если конструкция занимает несколько строк, пометка ставится на ту строку, куда
указывает находка, — то есть на начало команды:

```latex
\caption{Зависимость погрешности от числа % EXPECT
  измерений.}
```

Комментарий вырезается парсером и на разбор не влияет.

`good.tex` — файл, на котором правило не должно сработать ни разу. Это не формальность:
именно сюда складываются пограничные случаи, на которых легко получить ложное
срабатывание. Хороший `good.tex` содержит конструкции, похожие на нарушение, но
нарушением не являющиеся — точку внутри наименования, подпись таблицы там, где
правило проверяет рисунки, многозначное число в начале заголовка.

Оба файла обязаны разбираться парсером без замечаний.

## Параметры

Если у правила есть порог, который кафедра захочет изменить, объявите его
параметром со значением по умолчанию:

```python
@rule(
    id="G732-5.3.2.1-keywords-count",
    clause="5.3.2.1",
    severity=Severity.ERROR,
    title="Число ключевых слов вне допустимого диапазона",
    params={"keywords_min": 5, "keywords_max": 15},
)
def keywords_count(doc: Document) -> Iterable[Finding]:
    params = keywords_count.params(doc)
    lower = int(params["keywords_min"])
```

Профиль переопределяет параметр так:

```toml
[rules."G732-5.3.2.1-keywords-count".params]
keywords_max = 20
```

## Проверки

```bash
make check
```

Прогоняет `ruff check`, `ruff format --check`, `ty check` и `pytest`. Всё должно
проходить полностью. Отдельно:

```bash
make lint
make test
make format
```

## Что проверяет тест автоматически

- правило сработало на `bad.tex` ровно на помеченных строках;
- правило не сработало на `good.tex` ни разу;
- у каждой находки непустые `message`, `requirement` и `context`;
- `clause` находки совпадает с объявленным в декораторе;
- `suggestion` есть, если правило не объявлено с `allow_missing_suggestion=True`;
- у каждого правила есть каталог фикстур, у каждого каталога — правило.

Последние два пункта не дают репозиторию расползтись, поэтому обойти их нельзя.

## После добавления правила

Перегенерируйте страницы документации:

```bash
uv run nk rules docs
```

Каталог `docs/rules/` руками не редактируется: он собирается из реестра, а тест
проверяет, что записанное на диске совпадает со сгенерированным.

## Чего в правилах не делаем

- Не вызываем LLM: инструмент детерминирован.
- Не читаем PDF: источник данных — только исходники `.tex`. Проверки, требующие
  скомпилированного документа (поля, гарнитуры, кегль, колонцифры), в область
  видимости не входят.
- Не цитируем ГОСТ 7.32-2017 ни в коде, ни в тестах, ни в документации.
  Допустимы только номера пунктов и собственные краткие формулировки.
- Не правим файлы отчёта наугад. Правка объявляется только там, где замена
  однозначна; во всех остальных случаях правило ограничивается `suggestion`.
